## 背景与目标

当前微信桥接（`bridge.py`）是**单进程、纯被动**：`async for` 等鑫发消息才响应，没有任何主动推送能力。现实缺口：

- 时政简报由 systemd timer 每天 09:00 生成并落盘 md，但**不会发到微信**（鑫今天没收到）。
- 未来待办提醒、系统事件告警、MCP 提醒都需要主动触达微信。

**目标**：给 bridge 开一个本地 HTTP 外部消息入口，让各种外部源（系统定时任务、未来平台/MCP）能把内容推进微信；并经 agent 加工给鑫"处理建议"，而非机械通知。

## 架构决策

### 消息流程链
```
触发(定时/事件) → 决定发什么(大模型/规则) → 内容从哪来(数据源) → 怎么发出去(send_text)
```

### 三个核心取舍（已定）
1. **方案二：bridge 开外部入口**，而非内部自给自足。理由：时政 timer、系统事件等触发源与 bridge 解耦，不该塞进 bridge.py；bridge 当"发信通道 + agent 加工层"。
2. **接收并行、处理串行**：HTTP 能同时接收多个外部推送（不丢）；处理统一串行进 agent 会话（`asyncio.Semaphore`），保证人格统一、上下文连贯，不会多推互相覆盖。
3. **消息入口形态叠加**：直接发送（成品秒发）与喂 agent（需加工）并存，由 `type` 区分。

## type 分类（强制必带，缺则 400 拒绝）

按**处理方式**分（而非业务领域），起步 5 类（`chat` 对话类已删除）：

| type | 含义 | 处理方式 | 说明 |
|------|------|---------|------|
| `briefing` | 定时简报成品（时政等） | **direct** | 不占 agent 队列，原文发微信 |
| `file` | 文件原件 | **direct** | 把文件以附件形式发微信（实测可用） |
| `notification` | 一句话告知（下载完成等） | **direct** | 同上 |
| `text` | 通用文字 | **direct** | 最简兜底 |
| `reminder` | 提醒（待办/日程） | **agent** | 结合上下文生成提醒话术 |
| `alert` | 系统告警 | **agent** | 判断严重度 + 给处理建议 |

处理原则：direct 类不占 agent 处理，但发送仍统一走 send_text 队列（保证微信消息不乱序）；agent 类进串行队列，agent 加工后再发。

## 接口规范

- **端口**：`9898`（已定；避开 acp 45678、web 4096）
- **地址**：绑定 `127.0.0.1`（仅本机），外部任务都在本机
- **鉴权**：token（本地读 key 文件），防本机其他进程乱推
- **请求**：`POST /push`，JSON body
  ```json
  { "type": "briefing", "text": "简报内容" }
  ```
- **响应**：
  - 成功：`200 {"ok":true}`
  - 缺 type / 格式错：`400 {"ok":false,"error":"..."}`

## 反向回写（微信 → Obsidian 打勾）

**不做专门接口**。bridge 的 agent 直接改 vault 文件即可（与 opencode 用 write/edit 编辑 Obsidian 一致，零新依赖）：

- vault：`~/文档/private`
- 待办：`01-Todo/Todo-2026-MM.md`，形如 `- [ ] xxx 📅 2026-08-13`
- 打勾 = `- [ ]` → `- [x]`

闭环：微信"xx 办完了" → bridge 识别"办完"意图 → 在 01-Todo 找对应未勾项 → write/edit 打勾 → 回复。

弃用工具：`obsidian-cli`（实为 Obsidian QA 测试工具，无关）、`mcp-obsidian`（需装插件配 key 且只读，绕远）。

## 时政接入（当前唯一真实需求）

systemd timer 每天 09:00 产 md 到 `~/公共/时政简报/2026-MM-DD.md`，bridge 每天 09:00 轮询该目录。

**发送方式（已定，鑫 2026-08-14 拍板）**：产出文件后，bridge 检测到新简报 → agent 拿文件整理成**简短摘要**（200-300 字，重大事件为主，其他按需）→ 微信发**摘要文本 + 文件原件**（`file` 类型）双发。

实现：bridge 的 `briefing_worker` 每天 09:00 轮询，发现未发送的最新简报即触发；摘要由 agent 加工（走串行队列），原件走 `_send_file`（file 类型直发）。`sent_marker.json` 记录已发日期防重发。

既有两种做法中的 a（改 timer ExecStart curl push）未采用，采用 b（bridge 轮询），避免改动 timer 维护面。
